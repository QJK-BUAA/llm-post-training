    POMDP 掩码 轨迹

    1.1 一眼看懂多轮交互闭环：轨迹长什么样、掩码怎么打、POMDP 在说什么¶

    本节摘要

    先不背定义。看一条退货核查轨迹在上下文里到底由哪些词元拼成，分清哪些是模型写的、哪些是外部系统塞进来的，你就能自己推出两件事：环境返回为什么必须打掩码，以及为什么不知道环境的内部规律也能做梯度更新。最后再把这套过程压缩成 POMDP 七元组。

    先看显存里的一条轨迹¶

    用户说：「订单 42 能退吗？」模型和系统交替往同一条上下文里追加文本：

    [用户] 订单 42 能退吗？
[模型] <think>先查订单状态</think> <call>get_order(42)</call>        ← 模型写的
[环境] <obs>{"status":"shipped","days":3}</obs>                        ← 数据库塞进来的
[模型] <think>已发货 3 天，再查退货政策</think> <call>get_policy()</call>  ← 模型写的
[环境] <obs>{"return_window_days":7}</obs>                             ← 数据库塞进来的
[模型] <think>3 天在 7 天内</think> <answer>可以退货</answer>          ← 模型写的

    这就是一条轨迹 \(\tau\)。它和单轮数学题的唯一区别是：中间夹着模型没写、也没法控制的文本。

    训练时每个词元要不要算损失，只看一件事——它是不是模型采样出来的：

    片段 谁产生的 损失掩码 原因
    <think>、<call>、<answer> 模型按 \(\pi_\theta\) 采样 1 这是策略的动作，要奖要罚都落在这里
    <obs> 里的 JSON 数据库、搜索引擎、代码沙箱 0 不是模型选的，奖罚它没有意义
    用户原话 用户 0 条件，不是动作

    不打掩码会发生什么

    如果把 <obs> 也算进损失，答对时梯度会去抬高「数据库恰好返回的这串 JSON」的概率，答错时去压低它。模型会被迫背诵或回避外部文本的措辞，几十步后语言分布就被污染了。Search-R1 把这件事单独命名为 retrieved-token masking，本质就是上面这张表。

    为什么不知道环境规律也能算梯度¶

    整条轨迹出现的概率，是模型出招和环境返回交替连乘：

    \[ P_\theta(\tau)=\prod_{k=1}^{K} \underbrace{\pi_\theta(z_k,a_k\mid h_k)}_{\text{模型这一轮出招}} \cdot \underbrace{P_{\text{env}}(\text{obs}_k\mid h_k,a_k)}_{\text{环境这一轮返回}} \]

    取对数再对 \(\theta\) 求导。环境那一项不含 \(\theta\)，导数恒为零：

    \[ \nabla_\theta \log P_\theta(\tau) =\sum_{k=1}^{K} \Big( \underbrace{\nabla_\theta \log \pi_\theta(z_k,a_k\mid h_k)}_{\text{保留}} + \underbrace{\nabla_\theta \log P_{\text{env}}(\text{obs}_k\mid h_k,a_k)}_{=\,0} \Big) \]

    所以我们不需要知道搜索引擎内部怎么排序、数据库怎么调度。策略梯度只落在模型写的那部分词元上。代码里的掩码不是工程补丁，就是这一行求导逐词元落下来的样子。

    📖 初学者补充：这和单轮 GRPO 的掩码有什么不同？

    单轮 GRPO 里也有掩码，但那是把填充（padding）和提示词去掉，剩下的回答全是模型写的。多轮里多了一类要去掉的东西：环境返回。它在注意力计算时必须可见（下一步决策要读它），只是在损失里不计梯度。「能读」和「算梯度」是两件事，混淆这两点是多轮实现最常见的 bug 来源。

    奖励、回报和折扣：3 步手算¶

    给退货轨迹定一个简单的奖励：每次调工具扣 0.1（鼓励少绕路），最后结论正确给 +1.0，错误给 0。于是三轮的即时奖励是

    \[ r_1=-0.1,\qquad r_2=-0.1,\qquad r_3=+1.0 \]

    取折扣 \(\gamma=0.9\)。从第 \(k\) 轮往后能拿到的折扣回报 \(G_k=\sum_{j\ge k}\gamma^{j-k}r_j\)：

    从哪一轮算 计算 回报
    第 3 轮 \(1.0\) 1.00
    第 2 轮 \(-0.1+0.9\times1.0\) 0.80
    第 1 轮 \(-0.1+0.9\times0.80\) 0.62

    三件事值得注意。第一，越早的动作，回报里掺的折扣越多，所以「第一步就查对」和「绕了两圈才查对」在回报上天然有别。第二，\(\gamma\) 越接近 1，模型越愿意为长远收益忍受眼前的调用成本；\(\gamma\) 太小会变得短视，没查清就急着下结论。第三，这里的 \(G_k\) 是这一条轨迹实际走出来的结果，不是期望。后面所有信用分配方法，都是在想办法把这种「事后实际回报」和「动手之前的预期」比较出一个更干净的信号。

    终止和截断也要分清。任务做完、做错到不可挽回，是终止，后面没有回报。上下文满了、步数超限被系统掐断，是截断，任务本身没结束。截断处如果直接按回报 0 处理，会把「还没做完」误标成「做失败了」。实现里截断样本要么丢弃，要么用价值估计补上尾巴，不能和真失败混在一起。

    把上面这套过程压缩成 POMDP¶

    现在定义就只是简写了。多轮交互是一个部分可观测马尔可夫决策过程：

    \[ \langle \mathcal{S},\ \mathcal{O},\ \mathcal{A},\ \mathcal{P},\ \mathcal{R},\ \gamma,\ T\rangle \]
    元素 在退货例子里是什么
    状态 \(\mathcal{S}\) 订单系统、政策库、用户真实意图的完整世界状态，模型看不全
    观测 \(\mathcal{O}\) 每次工具返回的那段 JSON，只是状态的一个切片
    动作 \(\mathcal{A}\) \(\mathcal{A}_{\text{text}}\)（说给人看的话）\(\cup\) \(\mathcal{A}_{\text{tool}}\)（改世界或取信息的调用）
    转移 \(\mathcal{P}\) 调了 get_order 之后世界和观测怎么变，由外部系统决定，未知
    奖励 \(\mathcal{R}\) 调用成本、中间校验、终局对错
    历史 \(h_k\) 模型真正能依据的东西：请求 + 此前全部思考、动作、观测

    「部分可观测」是关键。模型永远拿不到 \(\mathcal{S}\)，只能拿 \(h_k\) 做决策。两个看起来一样的观测，可能对应不同的真实状态（比如订单页显示「已发货」，但仓库其实已拦截）。把表面相同的观测当成完全相同的状态，是后面信用分配会踩的坑，1.4 会回到这一点。

    对照单轮：传统偏好微调和单轮 RLVR 是 \(T=1\) 的退化情形——读一个提示，吐一整段，立刻终止，没有环境转移。经典强化学习本身就研究多步决策；退化成一步的是单轮微调，不是 RL。

    多轮训练循环和单轮差在哪几行¶

    # 单轮：采样一整段，判分，更新
answers = policy.sample(prompt, n=G)
rewards = verify(answers)
loss = grpo_loss(answers, rewards)          # 回答全是模型写的

# 多轮：模型和环境轮流往上下文里追加
for episode in episodes:
    history = prompt
    while not done and steps < MAX_STEPS:
        action = policy.generate(history)    # 思考 + 工具调用
        obs, reward, done = env.step(action) # 沙箱/搜索/数据库执行
        history += action + obs              # obs 只进上下文
        record(action, reward, mask=1)       # 只记模型写的部分
        record(obs, mask=0)
    loss = policy_gradient(recorded, rewards)  # 掩码在这里生效

    多出来的就是中间那个 while：环境执行、把观测拼回去、给每段文本打掩码。后面四节的所有算法，都是在这个循环的某一个位置做文章——1.3 改奖励怎么算，1.4 改功劳怎么分，1.5 改轨迹怎么采，1.6 改更新怎么稳。
