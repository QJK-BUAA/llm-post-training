    2.2 代码解释器、软件工程与终端智能体¶

    本节摘要

    代码场景分两层：先是推理时要不要调解释器验算（工具集成推理），再是到真实仓库里改几十个文件修 Bug（软件工程）。前者的验证器是执行结果，后者的是测试套件。本节讲 ReTool、ToRL、SWE-RL 这条线，以及它和后训练报告 2.10 里 GLM-5 工程细节的分工。

    第一层：工具集成推理（TIR）——写着写着，停下来算一算¶

    数学和代码推理里，模型常在心算上栽跟头。工具集成推理让它在推理中途生成一段代码、丢进沙箱执行、把结果读回来接着推。

    要素 内容
    状态 当前推导 + 已执行代码的输出
    动作 继续手写推导，或生成代码调用解释器
    奖励 终局答案对错；调用次数、代码报错率是常见辅助项
    难点 什么时候值得调工具：简单乘法也调，浪费且打断思路；该调时不调，心算错

    ReTool（arXiv:2504.14945）——注意它和 1.5 的 LUFFY 是两篇同期工作，名字像，做的事不同——系统研究了这种「战略性工具使用」：用 RL 让模型自己学会在关键计算处切换到代码，并从执行报错里改代码。ToRL、ToolRL 同属这一层，差别在奖励怎么计调用成本和格式。OTC-PO 这类工作专门优化调用效率：答对的前提下，调得越少越好。

    这一层的信用分配相对好做：代码执行成功与否是即时的、局部的信号，不用等终局。但要注意，别把「代码跑通了」当成「推理对了」——代码可以无报错地算出一个错误公式的结果。

    第二层：仓库级 SWE——面对一个真实代码库¶

    到了 SWE-bench 这类任务，场景完全变了：

    要素 内容
    状态 整个仓库的文件、Issue 描述、测试结果
    动作 搜文件、读代码、编辑、跑测试、看报错再改，几十步起
    观测 文件内容、终端输出、测试报告，又长又占上下文
    奖励 Fail-to-Pass 测试通过、Pass-to-Pass 不回归（定义见后训练报告 2.10）
    难点 定位（改哪个文件）比修改本身难；上下文装不下整个仓库；测试要跑几分钟，采样极贵

    SWE-RL（arXiv:2502.21936）的代表性在于数据来源：它从开源软件的真实演化历史（PR、提交）里构造训练信号，用较软的相似度奖励衔接，而不是只靠稀疏的测试通过。DeepSWE、SkyRL 一类工作把这条线推向长窗口和大规模异步采样。GLM-5、Kimi K2、MiniMax Forge 的工业实现（TITO、确定性 top-k、前缀树合并、异步新鲜度）在后训练报告 2.5、2.10 和本报告 3.1 里，这里不重复。

    信用分配在这个场景最痛：改对了第三个文件，前两个文件的错误尝试该不该罚？1.4 的 ELPO 二分定位在这里最自然——测试从红变绿的转折点往往就对应关键修改步。但每跑一次测试都要几分钟，二分探测的成本要按测试时间算，不是按步数算。

    终端智能体：命令的世界没有撤销键¶

    终端任务（装环境、排障、数据处理）和 SWE 共享沙箱，但动作更杂：任何 shell 命令都是动作，观测是千奇百怪的终端输出，奖励常是「最终系统状态是否满足某个断言」（文件存在、服务能启动、输出符合格式）。

    它多两个特有难点。一是不可逆动作：rm、覆盖写、改配置，错了没有逐步撤销，只能靠容器快照重置环境——这也是为什么这类训练全在可秒级复位的 Docker 里做。二是验证器要单独写：不像代码有现成测试，终端任务的验收脚本本身的质量决定奖励质量。任务合成时让另一个 Agent 写验收、再实测验收能不能区分对错解，是 GLM-5 等报告里的标准流程（见后训练报告 2.10 的 Terminal 合成）。

    评测对应 Terminal-Bench 这类基准。采样成本上，终端和 SWE 是所有场景里最贵的，这也是异步框架（3.1）和 Partial Rollout 在这里最先被逼出来的原因。

    三层共用的坑¶

    • 偷看答案：在仓库里 git log 能看到未来的修复提交。训练环境必须清洗 git 历史，这是 3.2 防作弊的第一条。
    • 改测试骗绿：把测试改松、删断言。测试目录只读挂载、验收与训练分离。
    • 硬编码过测：针对测试用例写特判。用隐藏测试集和随机化测试兜底。
