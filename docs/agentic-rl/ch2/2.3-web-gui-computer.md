# 2.3 网页与多模态 GUI 操控智能体

!!! abstract "本节摘要"
    GUI 场景把观测从文本变成了截图，把动作从生成文本变成了点坐标。这个变化带来三个新问题：看不懂界面元素在哪（定位）、几十步的截图历史塞不进上下文、没有现成测试能判对错。本节讲这条线怎么从 DOM 文本交互走到纯视觉操控。

## 这个场景长什么样

| 要素 | 内容 |
| --- | --- |
| 状态 | 操作系统或浏览器的真实状态 |
| 观测 | 截图（像素），或网页的 DOM / 无障碍树（文本） |
| 动作 | 点击 \((x,y)\)、拖拽、键入、滚动、热键，是连续或大离散空间 |
| 奖励 | 任务完成断言（订票成功、设置已改），常需专门的状态校验器 |
| 难点 | 视觉定位、长历史压缩、环境慢且难复现、安全（真实点击不可撤销） |

早期工作走 DOM 路线：把网页结构序列化成文本喂给模型，动作是点某个元素 ID。这绕开了视觉，但拿不到画布类应用和桌面软件。纯视觉路线直接看截图出坐标，通用，但把「理解任务」和「找到按钮在哪」两个难题叠在了一起。

## 三个代表节点

**WebRL**（[arXiv:2411.02337](https://arxiv.org/abs/2411.02337)）解决冷启动：从模型失败的任务里自演进出新课程（把没做成的任务改成相近的可练版本），配一个结果奖励模型判成败，让网页 Agent 能在线自我提升，而不是只靠静态示范。

**DigiRL**（[arXiv:2406.11896](https://arxiv.org/abs/2406.11896)）把训练搬到真实安卓设备环境里，用离线到在线的两段价值学习处理真实设备的噪声和不可复现性，是「野外设备」上做 RL 的早期代表。

**UI-TARS**（[arXiv:2501.12326](https://arxiv.org/abs/2501.12326)）代表原生 GUI 基础模型路线：统一的截图输入和动作空间，大规模 GUI 轨迹预训练打底，再用反思和迭代训练提升。后来的 MobileRL、OpenWebRL 把在线多轮 RL 和开源评测闭环补上，OpenWebRL 一类框架把浏览器基础设施、上下文管理和轨迹级裁判打包开源。

## 这个场景特有的三个技术问题

**视觉定位（Grounding）。** 模型说「点保存按钮」，要落成坐标 \((x,y)\)。定位错一格，后面全错，而且这种错和「决策错」混在一起，信用分配分不清是没看准还是没想对。常见解法是把定位单独训（用元素标注数据），或在奖励里把「点中目标元素」做成中间校验。

**长历史压缩。** 一步一张截图，30 步就是 30 张图，上下文和算力都爆。做法包括：只留最近几张截图加历史动作的文字摘要、把已完成子目标折叠成一句话（和 2.4 的上下文管理是同一问题在视觉侧的版本）、关键帧保留策略。

**验证器缺失。** 不像代码有测试，「机票订好了没」要查页面状态或后端记录。Interactive Reward Agent 这类工作专门训状态校验器。校验器本身是模型，就有被钻的可能：模型学会做出「看起来完成」的界面状态。校验要尽量落到后端状态，而不是截图观感。

## 安全是这个场景的一等公民

GUI Agent 的动作直接作用在真实系统上：点错链接、发错邮件、删错文件，都不可逆。训练必须在沙箱系统和快照里做；部署侧要有动作白名单、敏感操作二次确认和步数上限。这不是对齐的附加项，而是这个场景能不能上线的前提。评测常用 OSWorld、WebArena、VisualWebArena、AndroidWorld，比较时要注意它们的环境版本漂移很快，分数跨论文比较要谨慎（3.3 会展开）。
