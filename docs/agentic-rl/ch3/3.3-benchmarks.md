# 3.3 Agentic 评测基准全景地图与选型指南

!!! abstract "本节摘要"
    Agent 基准比数学基准难比得多：环境会漂移、判分方式各异、分数对版本敏感。本节按五大场景列主基准、它们怎么判分、各自的坑，最后给选型建议。

## 先立一条规矩

跨论文比 Agent 分数，先核四件事：**环境版本、模型规模与采样设置、是否用同一套验收、分数是单次还是多次平均**。四件有一件不同，差距就可能不是算法带来的。尤其是网页和 GUI 基准，网站本身在变，今天的 70 分和半年前的 70 分不是同一把尺。

## 五大场景的基准地图

| 场景 | 主基准 | 怎么判分 | 主要的坑 |
| --- | --- | --- | --- |
| 软件工程 | SWE-bench Verified、SWE-bench Live、Multi-SWE-bench | F2P 测试全过且 P2P 不回归（3.2 的验收方式） | Verified 是人工筛过的子集，和全量不是一回事；Live 版持续更新更防污染，但和旧分数不可直接比 |
| 终端 | Terminal-Bench | 任务结束时跑验收脚本查系统状态 | 环境构建失败要和任务失败分开计，别把基建故障算模型头上 |
| 工具调用 | BFCL（多版本）、\(\tau\)-bench、\(\tau^2\)-bench、AppWorld | 函数名与参数匹配、数据库最终状态、单元测试式断言 | BFCL 版本间题目和判分都变；\(\tau\)-bench 类强调多轮里用户意图变化和状态一致性，和单轮函数调用不是一回事 |
| 深度搜索 | GAIA、BrowseComp | 最终答案匹配（可核查、过程不限） | 网页漂移导致可复现性弱；要注明评测时间和检索后端 |
| GUI / 电脑操控 | OSWorld、WebArena、VisualWebArena、AndroidWorld | 系统状态断言、页面状态、任务脚本 | 版本漂移最快；截图分辨率、动作空间定义不同都会改分数 |

## 判分方式决定了基准在量什么

- **测最终状态**（SWE、终端、AppWorld）：最硬，最难作弊，量的是真把事办成没有。
- **测答案文本**（GAIA、BrowseComp）：量结果对错，不管过程是否绕路、引用是否属实。
- **测动作匹配**（部分工具调用集）：量和标准轨迹像不像。轨迹像不等于事办成——同一个目标可以有很多条正确路径，动作匹配会冤枉走新路的模型。

选基准时先想清楚你要量哪一种，再看榜单。

## 饱和与污染

老基准会逐渐饱和并被污染：题目进了训练数据、解法被反复研究、环境被摸透。应对方式是滚动更新（Live 类基准持续出新题）和留出私有集。报告分数时写明基准版本和日期，是这个领域的基本规范。

过程指标值得单独报：平均步数、工具调用次数、失败恢复率（第一次做错后能不能救回来）。只报成功率，会掩盖「靠试错 50 次撞对」和「3 步干净做对」的区别，而后者在部署时才是能用的。

## 选型建议

| 目的 | 建议 |
| --- | --- |
| 训代码 Agent | SWE-bench Verified 做主尺，Live 版做防污染对照 |
| 训搜索 Agent | BrowseComp / GAIA，并固定检索后端和日期 |
| 训 GUI Agent | OSWorld 或 AndroidWorld 二选一跑透，别追全榜 |
| 内部迭代 | 自建 200–500 条与业务同分布的留出集，比公共榜更能反映改动 |
| 发论文/报告 | 主基准 + 一个不同判分方式的副基准，并公开采样设置 |
